# 饮食目标推荐：技术设计

状态：iOS 首版已实现，待审阅，尚未发布。原方案保留完整演进方向，当前实施差异如下。

## 当前 iOS 实施

- 核心规则位于 `CookCore/DietaryGoals.swift`，JSON 标注和 Node 离线校验可供后续平台复用；本轮不实现 TS 推荐入口和 Web UI。
- 使用同包内的 `recipe-dietary.json`、`recipe-text.json` 和 `recipe-amounts.json`。标注记录图文指纹、配方字段指纹和整个用量文件的 SHA-256，先验证再形成候选，读到的正文即为冻结版本；不额外复制一份运行时正文。
- 用量文件独立变化会使旧标注整体失效；配方或正文变化会撤下对应记录。目标数据缺失或不兼容不阻断普通推荐。
- 当前 App 不支持在线菜谱更新，标注随 App 更新，独立 `dataVersion` 用于标识标注版本；第 4 节的在线更新与运行包机制暂缓。
- 系统 `List`／`NavigationStack`／sheet 选择单一目标，结果与已核对原文使用原生导航。目标阅读页显示核对理由和日期，并隐藏未经本功能核对的预估热量指标卡片。
- 本机记忆使用独立 `UserDefaults` 项，不修改 `Preferences` 或 CloudKit schema；目标推荐不进入现有食材排序／无结果信号，避免污染不含目标条件的评测。
- 第一批只开放“减少添加糖”“均衡搭配”。“控制体重”的数据类型和核对状态保留，入口未达到数据门槛，尚未开放。

以下各节是后续完整方案；与上述当前范围有差异的工作不列为本轮完成项。

## 2. 产品交互约定

目的：帮助用户从现有条件找到有具体依据的做法，不要求先填写身体数据。

视觉沿用 Cook 现有厨房风格与设计系统，不重做首页。Web 沿用项目字体栈、`--c-primary: #5fc178` 等现有 token；iOS 沿用原生控件、系统字体及现有 Chips／详情组件。字体与布局以现有项目规范为准，不引入字体、图片素材或新的图标体系。

- 在做菜筛选区域增加“饮食目标”单选入口及“不限目标”，使用现有组件密度与层级。
- 目标说明放在选择附近：控制体重显示“份量、用油参考”，减少添加糖显示“核对做法中的添加糖”，均衡搭配显示“看看还可以搭配什么”。
- 未选食材时展示已核对目标目录；选了食材后使用现有可做程度分组。目标状态在工作台、经典结果及随机页面可见。
- 结果行显示一条审核理由及“查看已核对做法”；详情显示完整原料、原始份数、来源、审核日期和相关证据。理由不挤占菜名及缺料信息。
- 目标上下文的主按钮打开已核对图文快照；“其他视频”“打开原文”为次入口，明确其来源区别。普通推荐维持原入口。
- 提供加载、更新失败、数据不兼容、无符合条件结果四种不同状态；未知数据不是加载中的占位零值。
- 默认只影响本餐；“记住这个目标”为显式本机选项。键盘焦点、屏幕阅读器、动态字体、深浅色和窄屏需要验收。
- Web 图文渲染只接受现有 block 类型与受控行内 Markdown，转义原始 HTML，验证外链协议及图片来源；不直接执行来源中的 HTML 或脚本。

## 3. 审核数据与来源

新增 `packages/data/recipe-dietary.json` 作为人工审核数据，新增 `packages/data/schema/recipe-dietary.schema.json`。不把目标结论写进 `recipe.csv.tags`，不改变既有菜谱 ID。

建议结构如下，字段类型及公开导出采用 TypeScript interface，示例只描述结构，不提供虚构的真实菜谱记录：

| 字段                  | 含义与约束                                                                                        |
| --------------------- | ------------------------------------------------------------------------------------------------- |
| `schemaVersion`       | 独立扩展 schema，首版为 1                                                                         |
| `policyVersion`       | 目标判断政策版本；修改判断语义时升级并重新审核受影响记录                                          |
| `goals`               | 稳定英文目标 ID、中文说明、开放状态；ID 为 `weight-aware`、`less-added-sugar`、`balanced-pairing` |
| `recipes[recipeId]`   | 只引用现有公共非负整数 ID；无效引用校验失败                                                       |
| `source`              | 首版 `kind: text`；保存原链接、已审核正文指纹、相关用量及食材／厨具字段指纹                       |
| `servings`            | 原始份数或明确的“每人份”依据，关联原文锚点；不默认按两人份处理                                    |
| `ingredientAudit`     | 完整原料与复合调料，逐项记录原名、可用标准名／显式别名、食物类别及锚点；区别于 `stuff` 摘要       |
| `assessments[goalId]` | `status: pass / fail / unknown`、固定理由代码、证据锚点、必要的未知原因                           |
| `perServingAddedOilG` | 仅在可复算时保存添加油克数的上下界、计算依据和份数；不能替代总脂肪                                |
| `pairing`             | 已核对的主食／蛋白质来源／蔬菜类别，及可补充类别的提示代码                                        |
| `reviewedAt`          | 审核日期；审核责任通过版本控制和 PR 保留，不公开反馈人信息                                        |

原文锚点复用 `recipe-amounts.json` 的 block／item／text 形式。用量公式复用既有解析器与求值规则，不另写正则猜测人数和克数。正文指纹与审核时相关用量、配方字段指纹一并校验。

源数据变化后，工具只报告过期记录，不自动重写审核指纹。审核人必须查看差异、更新证据及结论。AI 或脚本可以生成待审候选，但不能直接将未知记录升级为通过。

### 各目标判断与数值规则

1. **控制体重**：通过表示“具有份量及添加油参考”。要求配方用量和份数可核对；使用现有公式求得参考份数下的全部添加油，再除以参考份数。多个油项求和，范围上下界分别求和。存在不明油量、未确认条件分支、弃油／留存比例未知的煎炸过程时该项未知。只有原料和步骤均确认未加油时可记录零。首版只直接使用明确克数，不把毫升、勺、适量自动换为克。此数值不包含食材自身脂肪，不计算总热量。
2. **减少添加糖**：完整原料和步骤中未额外加糖，且糖、蜂蜜、糖浆、甜味酱汁、复合调料及可选项均经过核对。未知酱汁配方不能通过。天然含糖食物不自动排除；此目标不声称总糖或血糖反应。原文含糖而用户可自行省略时，首版仍不把原做法判为通过；调整版另行设计。
3. **均衡搭配**：根据完整配方人工确认食物类别，至少提供可解释的类别与一条搭配提示。分类用于提醒搭配，不按单道菜推断整餐达标，不计算食物份数比例，也不套用当前“食物相克”数据作为营养依据。

审核说明应分别列出正例、反例、未知例。G0 用 10 道不同来源情况的菜试标，并用第二遍复核确认判断可重复；缺乏依据的结论不以数量目标为由放宽。

## 4. 构建、分发与版本

新增校验器 `scripts/validate-dietary.ts`，拟新增命令 `pnpm dietary:validate`；接入现有数据校验／CI。检查 schema、ID、日期、目标与理由代码、锚点、来源指纹、数值范围、份数、完整原料审核、开放目标覆盖率。

新增构建步骤生成 `recipe-dietary-runtime.json`，内容包括经过校验的候选、展示理由、原始份数、所需图文快照和版本信息。Web 按需加载审核子集；不把全量 `recipe-text.json` 加入首屏。iOS 复用内置图文渲染，但必须确认展示的是同一已审核版本。图片沿用现有远程地址，文本可离线使用，图片失败不阻断做法。

- 运行包具有独立的 `schemaVersion`、`policyVersion`、`dietaryVersion`，以及匹配的目录和来源版本。`dietaryVersion` 覆盖审核内容与展示快照，单独改标注也必须触发更新。
- 在现有 meta 中增加可选的饮食扩展描述及版本引用；旧客户端忽略该可选扩展，保持现有主 schema 兼容。新增兼容测试，不因仅新增扩展强制旧客户端升级。
- `packages/cook/src/commands/convert.ts` 及配置负责生成和引用；Web 构建发布路径、缓存键及 PWA 需要包含新版本；`apps/ios/scripts/copy-data.sh` 和在线更新器需处理可选运行包。
- 两端下载至临时位置，验证完整包、版本及目录／快照对应关系后原子激活。不得先发布审核标签再加载另一版做法。
- 缺失、未知 schema、损坏或版本不匹配时保留普通菜谱；仅能回退到目录和来源仍匹配的上次有效审核包，否则暂停目标功能并显示原因。
- 编辑源数据后运行校验，再构建；源文件和审核指纹不一致必须使本次饮食包构建失败。

## 5. 推荐接口与排序

新增独立的目标候选模块（拟议路径 `packages/cook/src/utils/dietary.ts` 与 CookCore 对应文件）。增加可选目标上下文，不改变 `RecipeItem` 的基本身份或无目标推荐结果。

候选顺序：

1. 加载并验证目标数据，取当前目标 `pass`、来源及政策版本有效的公共菜谱集合。
2. 按完整审核原料排除忌口冲突；若复合配料或别名缺口使已选忌口无法判定，也排除该候选。排除大杂烩，应用工具、关键词、口味、难度与做法条件。
3. 有食材时接入既有推荐器计算主料匹配及缺料；无食材时走独立目标目录入口。
4. 有食材时按缺料数、大杂烩位置、命中食材数维持原优先级；在相同可做程度内，“控制体重”按每份添加油上界、下界升序，其余目标不增加未经验证的营养分。
5. 最后沿用视频质量分及源位置作稳定排序。无食材的目标目录按相应目标比较项、质量分、源位置排序；不显示食材已齐。

目标结果包含现有 match、固定理由代码、来源上下文与必要展示值。随机只从当前有效池抽取；补食材建议只统计目标池。收藏、历史和私人库的可见性不随目标筛选变化。

## 6. 状态、存储与隐私

Web 在 recipe store 持有当前目标，通过显式本机开关保存默认目标，遵守 `settings.keepLocalData`；iOS 在 `CookSession` 持有当前目标，每次选择自动写入独立本机设置，取消目标时删除保存值，不保留记忆开关。iOS 沿用原保存键以兼容旧目标，独立于现有 SwiftData `Preferences` 和云同步模型。不新增后端、账号权限或健康数据集合。

切换目标、经典／工作台视图、人数或筛选时，状态统一更新；点击“不限目标”同时清除本机记忆。清空本餐筛选不修改忌口，也不在当前会话恢复已记住的默认目标。

沿用现有固定动作统计机制，可增加 `open_dietary_goals`、`apply_dietary_goal`、`view_dietary_results`、`dietary_results_empty`、`view_reviewed_recipe` 等固定事件，不在名称、属性、URL 或日志中编码目标值。Web 目标控件和状态区域加入会话回放遮罩／排除，并检查实际行为。目标功能的错误日志只包含扩展版本与固定错误类别。

反馈复用现有菜谱纠错／意见反馈入口。做法版本可用于定位标注问题；不自动附带用户目标或健康信息。不新增公开工单同步。

## 7. 验证与风险

| 风险                     | 设计与验证                                                   |
| ------------------------ | ------------------------------------------------------------ |
| 将未知当成零或健康认证   | 三态模型；缺份数、未知糖酱、适量油、天然糖、可选糖等负例     |
| 图文与视频配方不同       | 目标主入口固定审核快照；测试另一来源不能继承标注             |
| 标注更新没有刷新         | 单独修改标注的更新测试；独立 dietaryVersion 与缓存键         |
| 新审核配旧正文或旧目录   | 整包校验与原子激活；跨版本、部分下载、过期来源测试           |
| 某个出口漏掉筛选         | 覆盖无食材目录、食材匹配、工具列表、随机、补食材及两种主视图 |
| 忌口只看主料或大杂烩例外 | 审核完整原料检查；大杂烩首版排除；不声称过敏安全             |
| 新偏好被同步或回放采集   | 独立本机存储；云同步序列化负例与回放遮罩验证                 |
| 两端结果不同             | 共享输入与预期快照；同时比较 ID、顺序、理由和油量范围        |
| 数据量不足               | G0 先试标，覆盖报告限制目标开放，不以误标补数                |

规则测试使用少量人工确定预期的合成边界案例；真实目录用例用于回归，不能只依赖由实现自动生成预期的快照。数据、规则及可见流程通过后才扩展验证范围。

## 8. 未来扩展边界

每份能量与宏量营养需要另选有许可的营养数据、明确生熟重／可食部、加工损耗和份数。届时再定义低能量、低碳水等政策，不能把首版添加油数据升级为总脂肪。生酮需要整日碳水与饮食模式设计；备孕、孕期分别需要专业内容审核和独立验收。本次不预建这些字段或规则。
