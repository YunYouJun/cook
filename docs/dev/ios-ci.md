# iOS CI 的时限与失败排查

PR 的原生验证按 iPhone、iPad 和三个测试组组成 6 个矩阵任务。每个任务只使用一台已有模拟器，禁用 XCTest 并行克隆；任务之间由 GitHub 分配独立 runner。

| 测试组               | 覆盖范围                                                                |
| -------------------- | ----------------------------------------------------------------------- |
| regression-main      | 全部 App 单元测试，以及下列分组之外的 UI 测试；新 UI 测试类默认进入此组 |
| regression-discovery | CloudKitchen、CookDiscovery、RandomRecipe                               |
| dietary              | 两个独立的可访问性审计，以及其余 DietaryGoals UI 测试                   |

`test/iosTestInfrastructure.test.mjs` 会回放真实 CI 脚本，逐个检查现有 UI 测试在每台设备上恰好分配一次。稳定的 `ios` 检查要求所有矩阵任务成功；只有已确认的纯文档改动可以跳过原生执行。

每个任务先 `build-for-testing` 一次，再用 `test-without-building` 复用产物。构建步骤上限 15 分钟、测试步骤 45 分钟、任务 75 分钟。普通单测默认上限 300 秒，两个较长的审计流程为 600 秒；任务超时仍会失败。上述时限不包含 GitHub 等待 runner 的排队时间。

同一 PR 推送新提交会取消旧 CI。矩阵保持 `fail-fast: false`，以保留另一台设备和其他测试组的结论。失败结果按设备与测试组分别上传，保留 7 天。

## 失败处理

- 业务断言和实际可访问性问题直接失败，不自动重试。
- 独立审计仅对结果包中已识别的审计服务超时、测试宿主启动停滞重试一次；原始失败结果保留，第二次失败仍失败。
- 审计优先在新的 runner 上执行，避免先跑长时间全量 UI 回归后才启动系统审计服务。
- `-collect-test-diagnostics never` 关闭失败后耗时的完整系统诊断收集；断言、测试日志、截图和 `.xcresult` 仍保留。需要系统级排查时，可针对单个失败用例改为 `on-failure`，不要直接重跑整个流水线。

## 2026-11-03 排查记录

[CI #667 的 iOS 任务](https://github.com/YunYouJun/cook/actions/runs/41341250755/job/124951611633) 从 19:20:57 UTC 运行到 22:50:13 UTC，约 3 小时 29 分钟，结论为 `failure`。Web 和 Swift 检查通过，两台设备的 214 项 App 单元测试均通过。

长耗时由两台设备串行全量 UI 回归、失败用例反复查询与滚动、审计超时重试共同累积。iPad 的一个用例寻找仅在窄屏存在的 `cook.showResults`，耗时约 375 秒；取消目标后读取原生菜单 `value` 得到空字符串；标准字号审计在 `dynamicType` 类别报 `Code=-56`。本地复现还确认，失败后 `simctl diagnose --timeout=600` 会继续占用时间。

对应修复：宽屏改为核对实际结果栏的目录数量；菜单标签直接提供当前饮食目标；筛选点击前确认整个选项露在固定汇总栏上方，并等待选中状态；iPad 输入联想后通过系统按钮收起键盘；滚动辅助方法按内容方向、所在栏和键盘遮挡定位，依次检查顶部食材和下方厨具时分别选择方向；灵感用例滚动收集三道菜的 ID，兼容 iPad 的懒加载；随机结果使用确定的无障碍元素类型查询，避免遍历整个应用的所有角色。
