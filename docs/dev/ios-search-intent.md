## S0 意图契约

`SearchIntent` 表达一次请求的解析草稿，不是推荐结果或可执行命令。模型和本地适配器使用同一契约，进入预览前先校验，确认应用前再次按当前数据与政策校验。

当前格式为 `{ schemaVersion: 1, dataVersion, policyVersion: 1, source, query, goal?, unresolved }`。`dataVersion` 必须等于当前加载的菜谱数据版本，`source` 仅接受 `local`、`mock`、`deepseek`，且必须与本次适配器匹配。`goal` 为单个 `DietaryGoal` 的原始值或空值；`unresolved` 为字符串数组。

| 内容                                 | 约束与现有实现的关系                                                                                                           |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------ |
| 食材、忌口、厨具、不吃辣、难度、做法 | 复用 `CookQuery` 的 `stuff`、`avoid`、`tool`、`noSpicy`、`difficulty`、`methodGroups` 语义；名称来自公共词典，别名规范到标准名 |
| 可选饮食目标                         | 最多一个，只接受当前 `DietaryCatalog.availableGoals` 中的目标；枚举存在不等于当前开放                                          |
| 待确认诉求                           | 模糊表达、词典外食材、冲突、未支持目标与无法核实的条件需显示给用户，不默默转成其他条件                                         |
| 解析来源                             | 区分本地与模型；mock 仅用于测试，不能成为线上 AI 状态                                                                          |
| 版本                                 | 携带意图格式、菜谱数据与政策版本；旧响应不能绕过当前词典和目标门槛                                                             |

根对象和嵌套 `query` 的未知字段、非法类型、词典外的标准值、不支持的版本、无效或未开放目标应拒绝；不能把部分非法响应当作成功条件应用。`query` 中的数组与 `noSpicy` 必填，`tool` 可选，`unknown` 必须为空；数组不得重复，`stuff` 与 `avoid` 不得交叉。输入最多 1000 字，响应 JSON 最多 32 KiB，每类条件最多 100 项，`unresolved` 最多 20 条不重复的非空文本，每条最多 500 字。模型输出不得包含最终菜谱 ID、新菜谱、热量、糖量、烹饪时间、账号状态、服务权限或自动执行指令。

普通词表搜索已有的 `CookQuery.unknown` 行为继续保留；智能草稿中的未知食材进入待确认项，不能通过模型输出直接扩展公共词典。无论来源如何，忌口优先于「有这个食材」，不会因模型建议静默放宽已有忌口。

### 草稿、确认与候选

1. 普通输入继续本地解析。用户主动进入条件预览时，先从本地规则生成草稿；只有显式选择智能找菜才有资格发起模型请求。
   原生搜索框输入后，点击建议中的「预览找菜条件」进入草稿；直接回车仍沿用原有个人词典和词典外食材逻辑。呈现预览期间保留搜索建议的状态，关闭弹层后再清空搜索框和结束搜索，避免同时移除建议按钮与呈现弹层造成生命周期竞争；普通提交有草稿存在时不会写入条件。
2. 预览独立保存，不改 `CookSession`、SwiftData 或饮食目标本机记忆。标签可以移除或修改，待确认项单独列出；不把它们描述成已生效筛选。
3. 用户确认后，将已验证条件交给现有会话逻辑。忌口和不吃辣沿用既有显式设置的持久化方式；目标记忆仍由用户控制，不在识别时自动开启。
4. 首版只检索内置菜谱。目标候选必须通过当前 `DietaryCatalog` 的数据指纹、原文锚点及目标状态校验；再与食材、忌口、厨具、做法等条件求交集，结果保留核对理由与实际做法来源。
5. 「控制体重」遵守既有开放门槛；痘痘、孕期、生酮、疾病饮食等不支持诉求进入说明或待确认项，不替换成已经开放的目标。无候选时显示无结果，不扩大目标池。

## 失败与请求状态

| 状态                                   | 行为                                                             |
| -------------------------------------- | ---------------------------------------------------------------- |
| 空输入或超长输入                       | 提示修正，不发模型请求，不改当前选择                             |
| 本地识别不完整                         | 展示可确认部分和待确认项，允许编辑或返回普通搜索                 |
| 无 Key、服务未配置、会员状态未知或过期 | 内置服务或对应模型路径不可用，本地识别可继续                     |
| 离线、超时或网络失败                   | 保留当前选择和本地草稿，允许重试或继续本地解析                   |
| 用户取消                               | 取消当前请求，不把取消展示为模型识别成功                         |
| 新输入或新请求取代旧请求               | 取消旧请求，并用请求身份隔离响应；即使取消后返回也不能覆盖新草稿 |
| 未知、非法或版本过期的响应             | 拒绝应用，显示可恢复错误，不执行模型给出的操作                   |
| 用户确认前数据或政策更新               | 重新校验；失效条件不能进入会话                                   |

失败与取消均不能清除原食材、忌口、目标或偏好。重试需要用户操作；模型不可用不阻塞本地做菜流程。

## 模型与设置

### 自带 DeepSeek API Key

设置提供模型总开关及自带 Key 的保存、替换与删除。Key 使用独立的 Keychain 项，设置 `kSecAttrSynchronizable = false`、`kSecAttrAccessibleWhenUnlockedThisDeviceOnly`；不写 UserDefaults、SwiftData、CloudKit、导入导出或日志，也不附在 URL 中。页面不回显已保存的完整 Key，测试使用内存存储，不触碰用户凭据。

数据流为「用户显式选择智能找菜 → 客户端携带个人 Key 请求 DeepSeek → 严格校验响应 → 可编辑草稿 → 用户确认 → 本地检索」。仅发送本次文本，以及解析所需的公共词典、当前可用目标和数据／政策版本。不会上传偏好、冰箱、私人菜谱、收藏、历史、账号资料或云乐坊会话。调用使用用户个人 DeepSeek 账户额度，不要求云乐坊会员。

请求使用固定 HTTPS 服务地址，不允许模型指定 URL 或变更目标服务；网络会话不共享 Cookie、不缓存请求或响应、不跟随携带凭据的重定向。超时、取消及迟到响应遵守上面的状态约束。开启功能与保存 Key 本身不等于同意后台调用，只有用户的显式模型操作才发送本次文本。

### 内置 DeepSeek：S2 服务端契约

内置服务仅供有效云乐坊会员。设置区分未登录、非会员、过期、服务不可用和资格待刷新；自带 Key 为独立路径，不通过内置服务转发个人 Key。

服务端约束与验证如下，实际线上与注入验收范围见[会员接入](./ios-managed-ai)：

- 从已验证会话确定非匿名 UID，检查账号可用状态；不接受客户端指定受益 UID 或 `isMember`。
- 在线读取平台会员有效状态及到期时间；缺失、过期、未知或读取失败均拒绝内置模型调用。现有平台账户服务 `account-api.getAccount` 返回 `{ coin, membership: { isActive, level, expireAt } }`；本次转发已验证用户的同一短期令牌，不给 App 或模型额外的内部服务凭据。
- 在调用模型前执行按身份的限流、输入大小限制、并发控制与服务预算检查。未配置预算、无法确认剩余额度、达到限制或上游异常时关闭该请求，不绕过校验直接调用。
- 平台模型 Key 只存在服务端。模型路由可替换；响应只给意图草稿及必要状态，不给客户端服务凭据或模型执行权限。
- 默认不保存原始饮食文本、待确认健康诉求或模型原始响应。日志与统计仅记录有限状态、耗时等诊断值，不记录文本、Key、token、账号资料或可还原用户诉求的数据。
- 同步更新实际对外数据流说明，并验收未登录、非会员、过期会员、会员失效、限流、预算耗尽及错误响应；前端限制不能代替服务端检查。

确认时做法和难度与当前选择取交集。新旧厨具、目标或做法／难度存在无法表达的冲突时，先提示用户修改，不写入任何条件，不能用空数组表示冲突后扩大成“不限”。模型遗漏本地已识别的食材、忌口、不辣、厨具、目标、做法和难度时保留本地约束；不同的目标或厨具拒绝响应。
