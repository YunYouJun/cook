# 0007 AI 能力：先做整句识别，AI 只负责听懂

- 状态：已采纳
- 日期：2026-10-19
- 补充：2026-10-28，按 [#181](https://github.com/YunYouJun/cook/issues/181) 单独推进 iOS 库内智能找菜
- 补充：2026-11-09，按 [#87](https://github.com/YunYouJun/cook/issues/87) 增加已有公开菜谱的逐步讲解
- 补充：2026-11-11，维护者明确模型功能集中在 App，Web 仅提供说明，并授权完成本里程碑合并与 #87 收尾
- 关联：[0003 原生 iOS App 与 monorepo 结构](./0003-native-ios-monorepo)（会员和「之后确定的高级功能」）

## 背景

- 用户想要「说一句话就出菜」：冰箱里有什么、不吃什么、想怎么做，现在要分别点食材、忌口、口味、厨具。
- 菜谱是人工整理的 600 多道菜，每道都对应一个 B 站视频，这是和通用 AI 助手不同的地方。
- 原则是尽量降低运营成本：免费用户零服务器成本，会员费覆盖云端开销（见 0003）。
- 端侧模型的设备、系统及地区覆盖需要按实际可用性判断，不能作为所有用户都能使用的前提。

## 方案对比

| 方案                            | 取舍                                                     |
| ------------------------------- | -------------------------------------------------------- |
| AI 生成菜谱、菜品图或做聊天助手 | 可能编出做不成的菜，成本随用户增长，和通用助手同质化     |
| 云端大模型理解整句              | 能补充词表之外的表达，需要模型费用、鉴权、限流及预算控制 |
| iOS 端侧模型理解整句            | 免费、离线，但覆盖机型和地区有限，Web 用不了             |
| **词表 + 最长匹配理解整句**     | 零成本、两端一致、可测；说法超出词表时认不出             |

## 2026-10-19 初始决定

- AI 只把用户的话翻译成现有筛选条件（食材、忌口、不辣、厨具、做法、难度），结果仍由推荐逻辑从现有菜谱里挑。不做 AI 编菜谱、菜品图和聊天。
- 第一步不用模型：`parseCookQuery`（`packages/cook/src/utils/query.ts`）按 `packages/data/query.json` 的词表做最长匹配，支持「不要 / 不吃 / 过敏」前后置否定、「没有」和「不辣」。用例在 `packages/data/fixtures/query.json`，Web 和 iOS CookCore 都要通过。
- Web 做菜页的输入框接受整句，识别结果写在输入框下方；只列食材时和原来一样。识别成功和失败分别上报 `parse_query`、`parse_query_empty`（只有事件名，不含输入内容）。
- 词表识别是两端共有的底线。初始方案优先 iOS 端侧增强，暂不提供内置云端模型，自带 DeepSeek API Key 作为后续选项。该服务边界已由下方 2026-10-28 决定替代。
- AI 不能挤占原生体验：
  - 不新增 Tab、独立 AI 页面或悬浮按钮。入口复用现有的搜索框；拍照识别做成搜索框里的一个小图标。
  - 点选食材的主流程不变。只有用户主动输入整句或拍照时才调用模型。
  - 模型可用性与具体入口按后续阶段验收；普通搜索始终可用。
  - 识别出的条件全部用现有的标签和筛选项展示，用户可以逐个移除。设置里有一个总开关，可以关掉 AI。
  - 不为 AI 引入影响启动速度或包体积的大依赖。

## 2026-10-28 补充决定

维护者明确要求按 #181 单独推进，先完成「自然语言 → 可编辑条件」，再接真实模型。以下规则替代初始方案中的「不提供云端模型」、端侧优先顺序及模型结果自动补充方式；尚未实施的能力不视为已经上线。

- 本轮仅接 iOS 库内检索；当时暂缓 Web 模型接入，其平台范围现以下方 2026-11-11 决定为准。普通输入继续走现有本地词表；模型请求只在用户显式选择智能找菜时发起。
- 识别结果先作为独立草稿展示：食材、忌口、厨具、做法、难度、不吃辣、一个已开放的饮食目标，以及待确认诉求。用户可修改或移除，确认前不写会话、SwiftData 偏好或目标记忆。晚到的模型结果不能自动覆盖当前筛选。
- 内置 DeepSeek 服务仅供云乐坊有效会员使用。登录身份不等于会员资格；服务端必须从验证过的会话确定 UID，再核验会员、请求限制及预算，不能相信客户端传来的 `isMember`。
- 普通用户可以在设置中填写自己的 DeepSeek API Key。请求由客户端直接发送到 DeepSeek，使用其个人账户额度；Key 仅存在本机 Keychain，不上传云乐坊，不随 iCloud、收藏、导出数据或日志同步。会员也可以选择自带 Key。
- 调用前明确说明数据去向：自带 Key 将本次输入及解析所需公共词典、可用目标与版本发送至 DeepSeek；内置服务将本次输入发送至云乐坊后端及模型服务。不得附带本机偏好、冰箱、私人菜谱、收藏、历史或账号资料。
- AI 只提取意图，不输出最终菜谱 ID、新菜谱或健康处方。客户端严格校验字段、公共词典、可用目标与版本，再由现有推荐引擎和来源校验决定候选。饮食目标只能缩小到当前有效的已核对候选，不能放宽忌口、厨具或其他明确条件。
- 本地草稿不需要会员或 Key。离线、取消、超时、响应非法或服务不可用时保留原选择，并允许继续本地搜索；未就绪的内置服务不能显示为可用的线上 AI。
- 拍照、联网搜菜、教学对话、多目标组合及健康档案不属于 #181 首版。模型费用、平台上线要求及端侧覆盖在实际接入时核对，本 ADR 不固定未验证的价格或发布结论。

契约、失败状态、分期及验收边界见 [iOS 库内智能找菜](../dev/ios-search-intent)。

## 2026-11-09 补充决定：已有菜谱逐步教学

维护者授权把 AI 从“提取搜索条件”扩展到“解释当前公开文本步骤”，但不改变 SearchIntent 契约、检索结果边界或现有会员基准。

- 教学只在用户主动点按「本步讲解」或「问这一步」时调用，绑定当前公开菜谱、原文指纹、稳定步骤 ID、份数和 AI 通道。缺少文本步骤时保留原入口与说明，不编造。
- 回答必须引用当前步骤原文；未知引用、版本或步骤漂移、超限、非法结构和新增数字/时间/温度均拒绝显示。引用与语法检查不能证明所有自然语言事实。
- AI 只解释，不替用户完成步骤，也不改变备料、份数、完成进度或计时器。回答只在当前页面内存中保留，切换上下文即取消旧请求并清除旧回答。
- 个人 Key 继续直连现有固定 DeepSeek 端点；会员教学使用独立 capability、契约和服务入口，不复用搜索 readiness。托管端从受信任、可重建的公开数据快照解析原文，不从客户端接收正文、任意 URL、userId 或会员标志。
- 会员教学重新核验账号与会员，复用现有 `cook_ai_quota` 总量控制；原始问题、回答、令牌和模型凭据不进入数据库或诊断日志。未部署、无 Key、离线或不合法响应不阻塞做菜。

详细实现、来源生成和验证范围见 [iOS 步骤讲解与提问](../dev/ios-step-guidance)。本补充不把尚未部署的托管服务、未执行的付费实调、TestFlight 或真机 VoiceOver 记作已验收。

## 2026-11-11 补充决定：模型集中在 App，完成首版收尾

维护者明确“Web 端就先不接入模型，接入模型功能留给 App”，并要求 Web 提供说明、完成合并、里程碑验收和 #87 收尾。

- Web 继续本地整句解析和现有菜谱筛选；模型功能集中在 App，目前实现为 iOS。Web「帮助」「关于」及官网定位／测试指南说明这一分工，不承诺后续 Web 模型接入。
- Issue #87 按“可选择模型通道、基于现有菜谱逐步引导”的 App 首版范围收尾；Gemini／免费模型、照片生成菜谱／配图等建议不作为关闭前提，也不记作已交付。
- 以已记录的定向测试、iPhone／iPad 模拟器流程、真实生产会员请求和内部构建 15 分发证据接受本里程碑。PR #210 已合并；Web 说明与关闭记录完成合并、线上核验后关闭 #87。
- 这项里程碑验收不代签个人 Key 或真机体验，也不代表维护者已逐条确认 AI 回答事实。人工待办继续保留，内部候选的 `maintainerContentApproved=false`、`physicalChecksVerified=false` 与 `acceptancePolicy=pending-physical` 不变。
- 步骤讲解仅内部分发。当前公开 TestFlight 邀请仍为构建 7，不扩大邀请、外测或 App Store 发布。

## 影响

- 新的说法靠补 `query.json` 词表覆盖；`parse_query_empty` 多了说明词表不够，再考虑上模型。
- 改词表或解析规则时要同时改 `fixtures/query.json` 和 CookCore 的实现。
- 忌口和「不辣」与手动勾选一样会一直保留，用户在识别提示里能看到生效的条件。
